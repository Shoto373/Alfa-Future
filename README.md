# Альфа.Пульс

Новостная аналитика для руководителей крупного бизнеса по кейсу Альфа-Банка × Changellenge. Сервис сопоставляет событие с компанией и ролью пользователя, объясняет риски, возможности и действия и показывает источники каждого утверждения.

Интерфейс оформлен по новым экранам Альфа-Бизнеса, предоставленным организаторами. Метрики качества, расходы LLM и журнал инструментов доступны сотрудникам банка (`OPERATOR_EMAILS`) через `/api/v1/metrics`, `/api/v1/metrics/daily` и `/api/v1/audit`; отдельная страница качества удалена в новом интерфейсе.

Основной сценарий: регистрация и вход → привязка компании и роль → персональная лента → разбор новости → вопрос → первоисточник → оценка. Пошаговая проверка — в разделе «Демонстрация». Это демонстрационный интерфейс Альфа-Бизнеса, без подключения к реальному интернет-банку.

## Запуск

**Требования к окружению:** Docker с Compose v2 (поддержка `env_file.required` и `--wait`), порядка 6 ГБ свободного места и 4 ГБ ОЗУ для контейнеров, свободные порты 3000, 8000 и 5432 (меняются через `WEB_PORT`, `API_PORT`, `POSTGRES_PORT`), доступ в интернет при первой сборке. Версии языков зафиксированы в образах: Python 3.11 (`python:3.11-slim`) и Node.js 20 (`node:20-alpine`, `engines.node >= 20.9.0`); зависимости закреплены в `backend/requirements.txt` + `constraints.txt` и `frontend/package-lock.json`. Mailpit (порт 8025) и Keycloak (8180) поднимаются только в необязательных профилях `mail` и `auth`.

Нужен Docker с Compose v2, поддерживающим `env_file.required` и `--wait`. Первая сборка скачивает базовые образы и локальную embedding-модель (~220 МБ) и занимает 10–20 минут; ключ LLM не обязателен — без него все сценарии работают на правилах. Для разработки без Docker — Python 3.11+ и Node.js 20.9+ (см. «Тесты и разработка»).

```bash
docker compose -f compose.yaml up --build -d --wait
```

Открыть **http://localhost:3000**. API: **http://localhost:8000/docs**. PostgreSQL доступен локально на порту 5432; БД и пользователь `alfa`, пароль по умолчанию `alfa-local`. Этот пароль предназначен для локальной разработки. Порты можно изменить через `WEB_PORT`, `API_PORT`, `POSTGRES_PORT`.

По умолчанию загружаются синтетические CSV из `data/synthetic`. PDF берутся из `data/materials/an`, если локальные материалы доступны. При отсутствии PDF весь сценарий работает, но переход к PDF возвращает «Документ не найден».

Полные CSV и PDF из предоставленного каталога `data`:

```bash
# Bash
CASE_DATA_DIR=./data BANK_PDF_HOST_DIR=./data/materials/an docker compose -f compose.yaml up --build -d --wait
```

```powershell
# PowerShell
$env:CASE_DATA_DIR = './data'
$env:BANK_PDF_HOST_DIR = './data/materials/an'
docker compose -f compose.yaml up --build -d --wait
```

В каталоге CSV нужны `df_Uid_data_hack.csv`, `df_Uid_payment_hack.csv`, `df_Fid_Uid_link_hack.csv`. В полном наборе проверены 85 514 уникальных компаний, 1 380 585 записей платежей и 12 514 связей физлиц; правило отбора дает 380 профилей. 115 компаний имеют собственную выручку свыше 15 млрд ₽, остальные включены по правилу надежной группы. Доля и место рассчитываются внутри выборки.

Смена набора меняет подпись источника, обновляет активные профили и инвалидирует кэш разборов. Файл `SYNTHETIC` должен быть именно файлом-маркером: одноименный каталог не обозначает синтетический набор.

```bash
docker compose -f compose.yaml ps
docker compose -f compose.yaml logs --tail=100 backend
docker compose -f compose.yaml down
```

Обычный `down` сохраняет том PostgreSQL. `down -v` удаляет данные: для перезапуска и обновления он не нужен.

Production-конфигурация использует nginx и существующие TLS-файлы. При прямом запуске Compose нужен `POSTGRES_PASSWORD` в `.env`, а также правильные `PUBLIC_ORIGIN`, пути к данным и сертификатам. Скрипт `deploy/prepare_env.py` при первой настройке сервера создает случайный пароль из 32 байт и сохраняет его в `~/app/.env` с правами `600`; для подготовки требуется Python 3 на сервере. Остальные настройки `.env` сохраняются, существующий пароль повторно не генерируется. Если том PostgreSQL уже существует, а пароль потерян, деплой остановится: нужно восстановить прежний `POSTGRES_PASSWORD`, не удаляя том. PostgreSQL в production не публикует порт на хосте. Тестовые задания CI/CD используют отдельную временную БД.

## Архитектура и хранение

```text
Браузер → nginx → Next.js / React (интерфейс Альфа-Бизнеса)
                → FastAPI × N (/api/v1, OpenAPI на /docs; без фоновых задач, ROLE=api)
Воркер (ROLE=worker, app/worker): очередь задач в PostgreSQL, сбор новостей, предрасчет, переклассификация
  ├─ auth: пользователи, членство в компаниях, роли, сессии
  ├─ companies: CSV → профили, группы, контрагенты, экспозиции
  ├─ news: RSS / URL / текст → полный текст → классификация (словари + смысл) → дедупликация, сюжеты
  ├─ knowledge: проверенные тезисы банка, гибридный поиск BM25 + векторы
  ├─ ranking: событие × компания × роль × свежесть × обратная связь
  ├─ agent: план → инструменты → черновик → проверки → коррекция → смысловая проверка
  │          └─ разрешенная LLM либо правила; каждый вызов инструмента — в журнале
  ├─ pipeline (воркер): сбор RSS → разборы заранее → AI-версии в пределах бюджета → отчет о качестве
  └─ quality: метрики, golden set, ежедневная сводка
PostgreSQL 17 + pgvector (данные, векторы, аудит, учет LLM) · Redis (кэш лент)
```

В PostgreSQL хранятся компании, метаданные импорта, новости, документы и тезисы банка, описания продуктов, история разборов, ответы на вопросы, отзывы, события, аудит инструментов и дневной учет LLM. Все 12 таблиц описаны типизированными ORM-моделями SQLAlchemy в `backend/app/models.py`; чтение и запись выполняются через `Session` и ORM-запросы. Входные и выходные контракты API валидируются Pydantic (`backend/app/schemas.py`). Таблицы используют ключи, внешние ключи, индексы, транзакции и JSONB для структурированных записей. Пользователи, членство в компаниях и сессии — тоже в PostgreSQL (таблицы `users`, `memberships`, `sessions`, `login_failures`).

CSV, `bank_analytics.json` и `seed_news.json` — источники импорта. PDF остаются файлами и подключаются только для чтения. Схемой управляет Alembic: ревизии находятся в `backend/alembic/versions`, текущая версия — в `alembic_version`. При старте выполняется `upgrade head` под транзакционной блокировкой. Начальная ревизия умеет принять заполненную схему предыдущего прототипа: проверяет маркер, состав и типы колонок, ключи и индексы, сохраняет записи и заменяет старый маркер версией Alembic. Неизвестная схема автоматически не принимается.

```bash
docker compose -f compose.yaml exec backend alembic upgrade head
docker compose -f compose.yaml exec backend alembic current
```

При изменении ORM-моделей создайте новую ревизию командой `alembic -c backend/alembic.ini revision --autogenerate -m "описание"` (с настроенным `DATABASE_URL`), проверьте операции и примените `alembic -c backend/alembic.ini upgrade head`. Примененные ревизии не редактируются. `alembic -c backend/alembic.ini check` проверяет расхождения моделей и схемы. Откат выполняется явной командой Alembic; откат начальной ревизии удаляет таблицы и данные и предназначен только для пустой тестовой БД.

Существующий JSON-runtime можно перенести отдельно:

```bash
docker compose -f compose.yaml exec backend python -m app.legacy_import --path /app/runtime
```

Импорт читает прежние файлы, сохраняет их, повторный запуск не дублирует записи. Архивные разборы помечаются требующими пересчета и не используются как актуальный кэш. При нарушенных ссылках транзакция откатывается; исходные файлы остаются на месте.

Намеренное изменение разборов — `UPDATE_CHARACTERIZATION=1 python -m pytest tests/test_characterization.py` и просмотр diff снимков.

## Отбор событий и достоверность

- Лента учитывает отрасль, продукты, ВЭД, отрасли контрагентов, роль и возраст события. Одного совпадения интересов роли недостаточно: нужна связь с компанией. Отсеиваются материалы без бизнес-тем, без такой связи и с оценкой ниже порога; внешние события старше 120 дней не попадают в ленту. Демо-события отдельно помечены и доступны для проверки. Исправлены ложные совпадения «стал», кинопроката, культурного вклада и запретов вне экономического контекста; одиночное слабое упоминание темы в анонсе недостаточно. Изменение словарей пересчитывает классификацию сохраненных записей и инвалидирует соответствующий кэш.
- Направление эффекта зависит от новости: снижение ставки может облегчить новые заимствования, но снизить доходность нового размещения. Наличие банковского продукта не сообщает остаток долга или условия действующего договора.
- Тезисы банка проверены по изображениям исходных PDF. Манифест `backend/app/knowledge/review.json` содержит результат по всем 43 тезисам, страницы и контрольные суммы. Исправлены восемь тезисов и неподтвержденный день публикации обзора золота. Материал о стали 2021 года и прогноз уже завершенного июльского заседания не используются как актуальная аналитика.
- Изменение прогноза определяется по одному показателю и горизонту. Разные даты обозначаются как пересмотр, разные значения на одну дату — как расхождение. Разные показатели и годы не объявляются противоречием.
- Утверждения помечаются как факт новости, данные компании, позиция банка или вывод AI. Заголовок строится правилами; резюме банка берется из проверенного тезиса. Свободный текст модели не становится официальной позицией банка.
- Проверки контролируют полноту, ссылки, тип источника, числа именно в указанных источниках, клиентские противоречия, доступность признаков, персонализацию, заголовок и резюме банка. После двух коррекций выполняется проверенный переход к правилам; если и он не проходит проверки, API возвращает явную ошибку.
- Отсутствие подходящей аналитики — допустимый результат с явным сообщением. Поиск не подменяется подбором случайного тезиса той же отрасли.

Проверки детерминированы и не доказывают смысловую истинность каждого AI-вывода. Семантическая оценка и полезность требуют отдельной экспертной проверки. Инструкции внутри новостей фильтруются и передаются модели как данные; это не заявляется полной защитой от всех видов prompt injection.

- Ранжирование: важность и вес роли берутся пропорционально доле темы в новости. Несколько признаков одной темы складываются с убывающим весом (1, 1/2, 1/4…), поэтому оценки не упираются в потолок. Учитываются также отрасли крупных контрагентов (от 15% платежей), регион компании (кроме Москвы и области: там «Москва» обычно означает государство) и сила события: «на 2 п.п.» сильнее, чем «сохранил». Похожие новости из разных источников склеиваются в один сюжет по смыслу заголовков. Фильтр тем показывает только темы, по которым у компании есть новости.
- Сила события (`app/news/magnitude.py`) определяется по числам в предложениях о главной теме и цитируется в разборе: «Масштаб изменения — сильное: в новости „на 2 п.п.“».
- Смысловая проверка (`app/agent/review.py`). Вторая модель (GLM с коротким рассуждением, около 0,04 ₽) получает каждый вывод AI с текстом его источников и решает: подтвержден, частично или не следует. Неподтвержденные выводы убираются, если раздел не опустеет и разбор снова проходит проверки. При сбое модели остаются детерминированные проверки, причина видна в трассе.

## Конвейер

Новости собираются и разбираются в фоне (`app/pipeline.py`), ручной кнопки обновления в интерфейсе нет. Цикл выполняет отдельный процесс — воркер (см. «Воркер и очередь задач»), API фоновых задач не запускает. Каждые `RSS_REFRESH_MINUTES` минут:

1. Сбор из источников (`app/news/sources/`): новые новости классифицируются, в базу попадают только деловые. Для RSS скачивается полный текст статьи по ссылке, если он содержит анонс (`RSS_FULL_TEXT`), иначе используется анонс ленты. Затем сюжеты новых новостей сохраняются в базе (`news.story_id`), а организации в текстах — в `news_entities`.
2. Сюжеты: новые сюжеты из трех и более сообщений об одном событии получают короткое название от быстрой модели (`PIPELINE_STORY_LABELS` за цикл, в пределах доли бюджета конвейера).
3. Разборы на правилах: для каждой привязанной компании и роли ее участников — `PIPELINE_RULES_TOP` самых релевантных новостей ленты без готового разбора. Пользователь открывает уже готовую карточку.
4. AI-версия: лучшие из карточек на правилах пересчитываются моделью — не больше `PIPELINE_LLM_PER_CYCLE` за цикл и пока конвейер не потратил долю `PIPELINE_LLM_SHARE` дневного лимита LLM. Карточку, черновик модели для которой уже не прошел проверки, конвейер повторно не пересчитывает.
5. Отчет о качестве: раз в сутки после `QUALITY_REPORT_HOUR_UTC` в Telegram уходит сводка (`app/quality.py`: доля текста модели, первая попытка проверок, источники, оценки, задержка, итоги конвейера), если заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Та же сводка — `GET /api/v1/metrics/daily`.

Цикл занимается в одной транзакции под `pg_advisory_xact_lock` с отметкой в `app_state`: за интервал его проходит один процесс, даже если воркеров несколько. Отметка упавшего посреди цикла процесса снимается через два интервала. Сбой источника RSS, вспомогательного шага (сюжеты, отчет), ленты одной компании или отдельного разбора записывается в лог и не останавливает цикл; сбой всего цикла — неудачная попытка задачи, очередь ее повторит.

### Источники новостей и организации в текстах

Каждый источник — адаптер с одним интерфейсом (`SourceAdapter`: `fetch(since)`, `health()`): RSS (`RssAdapter`, защита от SSRF и редиректов — `news/parser.py`), ручные материалы редакции (`ManualAdapter`, `MANUAL_NEWS_FILE`) и лицензированные ленты Интерфакс/ПРАЙМ (`LicensedFeedAdapter`). Реестр (`config.news_sources`, полностью заменяется JSON-файлом `SOURCES_FILE`) задает каждому источнику вес доверия, лицензию и частоту опроса. Лицензия `lead` — в базе только заголовок и лид, тело ленты не хранится. Ошибка одного источника не мешает остальным; число новостей, ошибок, задержка ответа и время от публикации до ленты по каждому источнику — в `app_state` (`news_sources`).

Лицензированные ленты без договора не подключаются: локально (`compose.yaml`) работает заглушка с демо-новостями в формате агентств (`LICENSED_FEED_DIR`, `app/news/sources/demo/`), в production ее нет.

Организации в новостях (`app/news/entities.py`) находятся без модели: названия компаний из профилей (в кавычках, после правовой формы или как слова с заглавной), ИНН и ОГРН с проверкой контрольных цифр, прочие организации «правовая форма + название в кавычках». Найденная компания профилей привязывается к `company_id`. В ленте у новости есть `mentions` (организации и их отношение к компании: своя, поставщик, покупатель) и признак `mentions_company`; в карточке — «Упоминается ваша компания / ваш поставщик», в разборе — блок «Упоминаются в новости». Сюжеты объединяются по смыслу заголовков с порогом `STORY_SIMILARITY` и хранятся в базе: перезапуск и повторный сбор их не пересчитывают.

### Аналитика банка из новых PDF (проверка аналитиком)

Сотрудник банка открывает «Тезисы аналитики» (`/admin/kb`) и загружает PDF обзора (до 20 МБ). Воркер (задача `kb_ingest`, `app/knowledge/ingest.py`) отправляет каждую страницу-скан визуальной модели `LLM_MODEL_VISION` (Qwen3-VL из списка кейса) и сохраняет черновики тезисов в `thesis_drafts`: тема, отрасли, показатель, значение, горизонт, страница и цитата. Расход на распознавание считается отдельной статьей бюджета LLM (`budget:kb_ingest`, доля `KB_INGEST_LLM_SHARE`).

У каждого черновика есть автоматические проверки: все числа тезиса есть в тексте страницы, цитата найдена дословно, дата документа распознана, тема из таксономии, нет дубля среди опубликованных тезисов. На экране скан страницы стоит рядом с черновиками. Аналитик правит черновик, публикует или отклоняет. Публикация добавляет тезис в базу знаний и в векторную коллекцию `thesis`. Прежний прогноз по тому же показателю и горизонту помечается `stale` со ссылкой на новый. Черновики агент не видит и как позицию банка не цитирует.

Кнопка «Загрузить демо-обзор» загружает синтетический обзор: сервер собирает PDF из картинок страниц `backend/app/knowledge/recorded/demo_page_*.jpg` (PDF в репозитории не хранятся), а ответы модели для него записаны (`KB_RECORDED_DIR`) — конвейер проходит без вызова модели. В одном черновике записана ошибка распознавания числа, чтобы проверка «числа есть на странице» была видна на экране.

### Наблюдаемость, алерты и бэкапы

`make up-monitoring` поднимает Grafana (http://localhost:3001: дашборды «Сервис», «Агент и LLM», «Воркер»), Prometheus с пятью алертами (бюджет LLM > 80%, p95 разбора > 30 с, 5xx > 1%, лаг новостей > 30 мин, бэкап старше 26 ч), Alertmanager (алерты уходят в Telegram-канал команды через backend), Tempo (трассы этапов агента) и сервис бэкапов: ежедневный `pg_dump` с ротацией 14 дней и еженедельная проверка восстановления (`make restore-test`). Логи — JSON с `request_id`, псевдонимом пользователя и `company_id`, без текстов новостей и профилей. Метрики каждого экземпляра API — `GET /metrics`; `trace_id` разбора — в `Insight.trace[*].output`. Что делать при каждом алерте — `docs/runbook.md`.

### Качество ленты: разметка и калибровка весов

Веса признаков релевантности лежат в `backend/app/ranking_weights.json` (с версией; подпись — в ключе кэша ленты). Сотрудник банка размечает пары «новость × компания × роль» оценкой 0–3 на экране «Разметка ленты» (`/admin/labeling`, 300 пар, 60 — двумя разметчиками для κ). `python scripts/eval_ranking.py --labels …` считает nDCG@10, precision@10 и долю нерелевантных в топ-3 по отраслям и ролям. `python scripts/fit_ranking.py --cv companies` подбирает веса попарной логистической регрессией с проверкой на отложенных компаниях. Отчет и порядок приемки весов — `docs/ranking-2026-11.md`.

### Отрасли, темы и действия как данные

Словари тем (стемы, смысловые описания, знак направления, формулировки эффекта, действия по ролям, уточняющие вопросы), отрасли (ОКВЭД, слова в новостях, чувствительность к темам) и слова-маркеры классификатора лежат в `backend/config/sectors/*.yaml`. Модули `news/taxonomy.py`, `companies/sectors.py` и `agent/composer.py` отдают те же объекты из `app/domain_config`. Эквивалентность прежним словарям в коде подтверждают характеризационные тесты ленты и разборов.

Сотрудник банка правит YAML на экране «Отрасли и темы» (`/admin/config`) и нажимает «Проверить». Валидатор `python -m app.domain_config.validate config/sectors` проверяет схему, ссылки, конвенцию знаков (`direction_value.up > 0`) и эталоны знака (`control_cases`: «рост ставки — риск для стройки»), а также запрещает числа в действиях. Перевернутый знак не публикуется. Превью показывает, как изменится лента выбранной компании. Публикация сохраняет версию в PostgreSQL: все экземпляры API применяют ее не позже чем через 5 с, а воркер переклассифицирует новости. Откат — публикация прежней версии. Подпись версии входит в ключи кэша ленты и разборов.

### Потоковый разбор

Страница разбора получает его потоком (`GET /api/v1/insights/stream`, Server-Sent Events). Сначала, за доли секунды, приходит проверенный разбор на правилах — разделы и источники. Затем приходит ход работы модели: план, сбор данных, черновик, проверки. Шапка показывает, чем модель занята сейчас. В конце приходят разделы версии модели, прошедшие те же проверки (`section_replaced`), и итоговый разбор (`done`). Непроверенный текст в поток не попадает. Уход со страницы закрывает поток и останавливает разбор моделью. Если SSE недоступен (прокси), интерфейс сам переходит на прежний `POST /insights`. Независимые инструменты агента выполняются параллельно; nginx не буферизует поток (`X-Accel-Buffering: no`).

### Граф контрагентов и мониторинг

Из платежей кейса строится граф «кто кому платит» (`app/companies/graph.py`): поставщики и покупатели с долей в платежах, их контрагенты (второй уровень, вес доля₁ × доля₂), возможные связи через общих физлиц. Воркер каждые 5 минут ищет новости, где названы контрагенты компании (организации в новостях из SPR3-02), и сохраняет алерт с цепочкой «вы → поставщик А (32% закупок) → его поставщик Б (51%)». Такая новость поднимается в ленте (признак `counterparty`), а разбор называет цепочку со ссылкой на `client:graph`. Экран «Контрагенты» (`/pulse/counterparties`) состоит из блоков «С кем вы связаны» (поставщики и покупатели с долей платежей и уровнем риска, карточка контрагента по нажатию), «Что произошло у контрагентов» (новости за две недели с цепочкой связи, в том числе через второй уровень), «Аналитика: от кого вы зависите» и «Возможные связи через общих физлиц». Отдельного блока второго уровня на экране нет: он виден в цепочках событий. Подробности и профиль графа — `docs/graph.md`.

### Сценарии «что если»

Панель «Что если: во что это обойдется» на странице компании и под разбором новости о ставке, курсе или сырье считает чувствительность компании по прозрачным формулам (`app/scenarios/calc.py`, `POST /api/v1/scenarios`); модель чисел не считает.

- Ставка → процентные расходы: долг × доля плавающих ставок × изменение ставки. Если долг не указан, он оценивается по отраслевому коэффициенту «долг/выручка» из доменной конфигурации (`finance` в `sectors.yaml`) с пометкой «оценка».
- Курс → валютная выручка и импортные закупки: доли сообщает компания или вводит пользователь.
- Цена сырья → маржа сырьевых отраслей.

У каждого входа есть происхождение: данные кейса, сообщила компания, оценка по отрасли, указал пользователь. «Коридор банка» берется из прогнозов в опубликованных тезисах. Если данных не хватает, расчет показывает, чего не хватает, а не ноль. Разбор новости о ставке содержит «каждый +1 п.п. — ≈ X млн ₽ в год» со ссылкой на расчет (`client:scenario:key_rate`): без формулы проверка цифр это число не пропустит.

### Воркер и очередь задач

Один образ backend, два процесса: `ROLE=api` — HTTP API, `ROLE=worker` — фоновый воркер (`python -m app.run`; воркер — также `python -m app.worker`).

- **Очередь** — таблица `jobs` в PostgreSQL, без отдельного брокера (`app/worker/queue.py`). Задачу берет ровно один воркер (`SELECT … FOR UPDATE SKIP LOCKED`); упавшая задача повторяется через 30 с, 1, 2, 4 мин…; после 5 попыток — `status=dead` с текстом ошибки (dead-letter). Если воркер упал посреди задачи, после окончания аренды (30 мин) ее берет другой.
- **Расписание** (`app/worker/schedule.py`): `news_cycle` — каждые `RSS_REFRESH_MINUTES` мин, `news_reclassify` — 10 мин (переклассификация при смене словарей и векторы заголовков), `warm_feeds` — 15 мин (ленты в общем кэше Redis), `llm_sweep` — 5 мин (зависшие резервы бюджета), `jobs_cleanup` — раз в сутки. Плановая задача ставится один раз за интервал (`dedupe_key`), даже при нескольких воркерах.
- **Остановка** по SIGTERM: новая задача не берется, текущая доделывается. Остановленный воркер не мешает API — новости просто не обновляются; после запуска накопленные задачи выполняются.
- **API** при старте загружает модель, векторы и новости в память; при изменениях подгружает из базы только измененные новости (`news.updated_at`), а не весь набор.
- **Наблюдение:** `GET /api/v1/meta` → `worker`: `alive` (пульс не старше 2 мин), `workers`, `last_seen`, `last_job`, `queue` (`queued`, `running`, `dead`, `oldest_ready_seconds`).

Локальный `compose.yaml` поднимает `API_REPLICAS` (по умолчанию 2) экземпляров API, один `worker` и `nginx`, который распределяет запросы по экземплярам (`nginx/local.conf`; упавший экземпляр пропускается) и отвечает на `http://localhost:8000`. Проверка через nginx — `make smoke`.

Статус последнего цикла общий для всех воркеров и отдается в `GET /api/v1/meta` → `pipeline`: `state` (`idle`, `running`, `disabled`), `started_at`, `rss` (добавлено, дубликатов, отсеяно, с полным текстом, недоступные источники), `stories_named`, `pairs`, `rules_built`, `llm_built`, `llm_skipped` (причина), `quality_report` (отправлен ли отчет), `duration` (секунды), `error`.

`RSS_REFRESH_MINUTES=0` выключает цикл новостей (остальные плановые задачи воркера работают); так он работает в тестах и, до релиза, в production Compose (`docker-compose.yml`). Локальный `compose.yaml` использует значение по умолчанию — 15 минут.

## Качество разборов

Качество измеряется на golden set — 31 синтетическая пара «новость × компания × роль» (`backend/tests/golden/cases.json`): ключевая ставка, курс, санкции, сырье, логистика, инфляция, налоги и три новости не про бизнес. Для каждой пары до прогона записаны ожидания: тема новости, знак влияния на компанию (риск, возможность, оба, зависит от операций, нет влияния), тема обязательного тезиса банка и запрещенные утверждения.

```bash
cd backend
python -m app.eval_quality --set tests/golden --mode rules --out q.json --md q.md   # без модели
python -m app.eval_quality --set tests/golden --mode llm --md q-llm.md             # с ключом LLM
```

Метрики: прохождение проверок с первой попытки и финальных, доля выводов со ссылкой на собранный источник, найденная тема, совпадение знака эффекта, тезис банка по теме, отсутствие запрещенных утверждений, причины провала первой попытки по коду проверки, задержка p50/p95, токены и стоимость LLM. Порог в CI (`tests/test_golden_quality.py`, режим правил): с первой попытки ≥ 80%, источники — 100%, без запрещенных утверждений — 100%, тема и знак — ≥ 90%. Отчет прикладывается к прогону CI как артефакт `quality-report`.

Замер на golden set, режим правил, 23.10.2026:

| Метрика | CI, без embedding-модели: было → стало | Как на проде, с моделью: было → стало |
|---|---|---|
| Прошли проверки с первой попытки | 100% → 100% | 100% → 100% |
| Выводы с источником | 100% → 100% | 100% → 100% |
| Тема найдена | 97% → 100% | 97% → 100% |
| **Знак эффекта совпал** | **70% → 100%** | **67% → 100%** |
| Тезис банка по теме | 88% → 88% | 100% → 100% |
| Без запрещенных утверждений | 100% → 100% | 100% → 100% |
| Задержка p95 | 0,05 → 0,04 с | 0,08 → 0,03 с |

В режиме правил проверки с первой попытки проходят все разборы; ошибки были в смысле, а не в форме. Исправлены три причины неверного знака, каждая закреплена тестом в `tests/test_analysis_quality.py`:

1. Курс читался без учета валюты: «рубль ослаб» распознавался как снижение курса, и ослабление рубля для экспортера выглядело риском. Теперь глагол при рубле читается наоборот, при иностранной валюте — прямо.
2. Направление не распознавалось по формам глаголов («ускорилась», «вырастут», «повысить», «проиндексирует»), а у санкций его не было вовсе — инфляция, налоги, тарифы и санкции получали «знак зависит от операций». Добавлены формы глаголов и направление санкций (вводятся — ужесточение, снимаются — ослабление).
3. Тема, найденная по смыслу и без своих предложений, получала направление другой темы: «ставка повышена» превращалась в «экономика растет — возможность». Теперь у такой темы направления нет. Словарь логистики дополнен погранпереходами и сроками доставки.

После замера в набор добавлен 31-й кейс с реальной ленты: «Экономист — о ключевой ставке, укреплении рубля и прогнозах ЦБ» при сохранении ставки. Слова «укрепление рубля» из общего словаря направлений переносились на ставку, и разбор обещал заемщику удешевление кредита вместо «деньги остаются дорогими». Теперь ослабление и укрепление рубля учитываются только для курса; кейс проходит, знак на всех 31 кейсах — 100%.

Без embedding-модели тезис банка ищется только по словам, и в двух кейсах по курсу («рубль» и «рубля» — разные слова) не находится; с моделью, как на проде, — 100%. Прогон в режиме LLM требует ключа и в CI не выполняется; его стоит повторить перед сдачей той же командой с `--mode llm`.

## Смысловой поиск (эмбеддинги)

Кроме словарей используется локальная embedding-модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (ONNX через `fastembed`, ~220 МБ). Она не генеративная: правило кейса о списке LLM на нее не распространяется. Модель скачивается при сборке образа и в работе не обращается к сети.

- **Темы новости по смыслу** (`app/news/semantic.py`). Новость сравнивается с описаниями тем (`TOPIC_MEANINGS` в `taxonomy.py`). «Мегарегулятор оставил стоимость заимствований» относится к ключевой ставке, хотя слова «ставка» в ней нет. Чтобы не тянуть в ленту политику, спорт и происшествия, новость сначала сравнивается с примерами «не про бизнес», и тема по смыслу добавляется только с запасом над ними. Если словари уже нашли темы, по смыслу добавляется не больше двух. Санкции и в этом случае требуют делового контекста. Если словари не нашли ни одной темы, тема по смыслу добавляется только при деловых словах в тексте (деньги, цены, компании, рынок, кредит — `BUSINESS_CONTEXT_STEMS`): модель путает с ключевой ставкой сам жанр «ведомство приняло решение», и без этого правила новости про ОБСЕ или удостоверение учителя попадали в ленту с темой «Ключевая ставка». Тема по смыслу получает вес слабого словарного совпадения и помечается «по смыслу (0,xx)».
- **Гибридный поиск по аналитике банка** (`app/knowledge/kb.py`). Оценка складывается из BM25 и смысловой близости тезиса. Тезис, сформулированный другими словами, проходит фильтр, если он лучший по смыслу среди тезисов нужной темы.
- Пороги подобраны на ленте RSS и тезисах кейса. На 113 новостях смысловые темы добавились к 10, из них 8 бесспорны. Веса отраслей и ролей по-прежнему заданы вручную.
- Если модель недоступна или `EMBEDDINGS_ENABLED=0`, сервис работает только на словарях и BM25. При включении или смене модели сохраненные новости переклассифицируются.

## LLM

Без ключа все основные сценарии работают на правилах. Для подключения скопировать `.env.example` в `.env` и задать:

```dotenv
LLM_BASE_URL=<адрес шлюза кейса с /v1>
LLM_API_KEY=<ключ команды>
LLM_MODEL_COMPOSE=deepseek/deepseek-v4.1-flash   # текст разбора
LLM_MODEL_PLAN=z-ai/glm-5.3-flash                 # уточняющие запросы к аналитике банка
LLM_MODEL_REVIEW=z-ai/glm-5.3-flash               # смысловая проверка (не та модель, что писала разбор)
LLM_MODEL_QA=deepseek/deepseek-v4.1-flash         # ответы в чате
LLM_DAILY_COST_LIMIT=450
```

Модели выбраны по сравнению всех шести моделей кейса на одной реальной задаче (разбор ставки ЦБ для компании): DeepSeek-V4.1-Flash написал самые конкретные выводы (26 с, 0,28 ₽), GLM-5.3-Flash — быстро и точно (13 с, 0,12 ₽), Qwen3.6 дал меньше выводов (30 с), Gemma 4 — общие формулировки (5 с), Kimi-K2.6 потратил больше 7000 токенов на рассуждения и не вернул ответ (77 с, 3,7 ₽).

Backend ограничивает модели списком кейса. При ошибке соединения используются запасной шлюз и предохранитель, затем правила; причина отображается в трассе. Дневные токены, стоимость, вызовы и ошибки сохраняются в PostgreSQL.

**Бюджет с резервированием** (`app/llm_usage.py`). Перед вызовом модели оценка его стоимости (токены запроса + `max_tokens` по цене модели) резервируется в строке дня одним атомарным `UPDATE … RETURNING` — только если потрачено + уже зарезервировано + новый резерв укладываются в `LLM_DAILY_COST_LIMIT` (рубли; лимит токенов `LLM_DAILY_TOKEN_LIMIT` — только если задан, по умолчанию выключен). Параллельные вызовы проверяют условие по очереди на свежих значениях, поэтому вместе превысить лимит не могут (тест: 20 одновременных вызовов при лимите на 5 — ровно 5 выполняются, 15 откатываются к правилам). После ответа списывается факт (`usage.cost` шлюза, а если его нет — по цене модели), при ошибке резерв снимается, зависшие резервы старше 10 минут снимаются автоматически. Цены моделей для оценки — `config.LLM_PRICES`, с запасом; переопределяются `LLM_PRICES=deepseek=0.05,glm=0.03`. Отказ бюджета — обычный откат к правилам с причиной в трассе. Разбор хранит причину отката в `fallback_reason` (`disabled` — ключ не задан, `paused` — AI выключен банком, `budget` — лимит дня, `company_budget` — доля компании, `unavailable` — модель не ответила, `checks` — выводы модели не прошли проверки), и карточка говорит пользователю именно ее, а не общее «AI недоступна». Без ключа это спокойная информационная плашка «AI-модель не подключена», а не предупреждение: для готовых разборов конвейера причина определяется в момент открытия. В `/api/v1/metrics` → `ai`: `reserved_cost`, `rejected_by_budget`, `fallback_rate` (доля разборов, где модель вызывалась, но итог — на правилах) и `llm_by_model` — расход за день по моделям с фактической ценой за 1000 токенов рядом с оценкой резерва: по ней цены в `LLM_PRICES` уточняются после первого дня с ключом.

**Защита общего бюджета.** Ключ один на всю команду, а лимит — общий на сервис, поэтому:

- **Доля компании.** Вызовы модели в разборе и чате резервируются и в доле компании (`LLM_COMPANY_SHARE`, 20% дневного лимита): одна компания не израсходует день за всех. Отказ по доле — тот же откат к правилам; в `/metrics` → `llm_by_company` — расход и отказы по компаниям.
- **Частота на пользователя.** «Пересчитать» и вопросы в чате ограничены за час (`LLM_USER_REFRESH_PER_HOUR`, `LLM_USER_QUESTIONS_PER_HOUR`), превышение — `429 RATE_LIMITED`. Без подключенной модели ограничение не действует.
- **Один разбор — один раз.** Если тот же разбор (компания, роль, новость) уже строится — другим сотрудником или конвейером, — второй запрос ждет первый и получает его результат: модель вызывается и оплачивается однажды. Действует внутри процесса.
- **Оповещения.** При пересечении 50%, 80% и 100% дневного лимита команда сразу получает сообщение в Telegram (`app/notify.py`), по одному на порог за день даже при нескольких воркерах — неожиданный расход (в том числе чужое использование ключа) заметен в течение часа, а не в утренней сводке.
- **Экономный режим.** С `LLM_ECONOMY_AT` (80%) дневного лимита черновики и ответы чата пишет более дешевая модель `LLM_MODEL_ECONOMY` (GLM вместо DeepSeek): AI-версии держатся до конца дня дольше. Модель видна в трассе разбора.
- **Выключатель AI.** Сотрудник банка (`OPERATOR_EMAILS`) выключает и включает вызовы модели без удаления ключа с сервера: кнопкой в профиле (блок «Сервис банка», виден только сотрудникам банка) или `POST /api/v1/ops/llm {"paused": true}`, состояние — `GET /api/v1/ops/llm`. Пока выключено, разборы строятся правилами, в карточке — «AI временно выключен банком». Для подозрения на утечку ключа и на время защиты.

**Предрасчет демо.** Чтобы на защите разборы открывались из кэша и не зависели от скорости провайдера:

```bash
docker compose -f compose.yaml exec backend python -m app.precompute_demo --dry-run   # план и оценка стоимости
docker compose -f compose.yaml exec backend python -m app.precompute_demo             # построить
```

По умолчанию — крупнейшие металлург и автодилер набора, роли CFO, CEO и собственник, пять лучших новостей ленты каждой роли (30 разборов); `--company`, `--roles`, `--top` меняют выбор. Скрипт идемпотентен: готовые разборы не перестраиваются (с подключенной LLM разбор на правилах улучшается моделью). Печатает время, токены и стоимость. `--max-cost 50` ограничивает расход на модель: когда следующий разбор может выйти за предел, остальные строятся правилами — бюджет живой демонстрации не тратится. В конце каждый демо-разбор открывается из кэша с замером времени; если какой-то открывается дольше 2 с или не из кэша, скрипт завершается с ошибкой.

## Тесты и разработка

Воспроизводимый backend-прогон с PostgreSQL и синтетическими данными:

```bash
docker compose -f compose.yaml --profile test run --build --rm tests
```

Тесты создают отдельную случайную схему и удаляют только ее. Они проверяют API, 30 поведенческих сценариев, источники, отказы модели, миграции, конкурентные записи, импорт и предрасчет. Не направляйте тесты в стороннюю или production-БД.

Для локальной разработки нужны Python 3.11+ и Node.js 20.9+. Зависимости backend и транзитивные версии закреплены в `requirements.txt` и `constraints.txt`; frontend — в `package-lock.json`.

```powershell
docker compose -f compose.yaml up -d postgres
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
$env:DATABASE_URL = 'postgresql://alfa:alfa-local@127.0.0.1:5432/alfa'
$env:PYTHONPATH = 'backend'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В другом терминале:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://alfa:alfa-local@127.0.0.1:5432/alfa'
.\.venv\Scripts\python.exe -m pytest backend/tests -q
cd frontend
npm ci
npm run build
npm run typecheck
npm run test:coverage   # unit-тесты интерфейса (vitest): слой данных, API, сессия, компоненты разбора; покрытие lib/ ≥ 70%
npm run budget          # бюджет главной: JS ≤ 200 КБ gzip (после build)
npm run start
```

Слой данных интерфейса — `frontend/lib/query.ts`: ответы кэшируются по ключу, одинаковые запросы объединяются, устаревшие обновляются в фоне. Переход «лента → разбор → назад» не загружает ленту заново; после добавления новости, входа и выхода кэш сбрасывается. На телефоне и планшете (до 860 px) — нижняя навигация; на планшете (768–1100 px) разбор открывается рядом с колонкой ленты, а боковое меню при горизонтальном планшете сжимается до значков; ссылка на чужую компанию (`?company=…`) или ответ 403 показывают экран «Нет доступа к компании». Три ширины (375/768/1280), кэш ленты, экран доступа и LCP главной проверяет `e2e/responsive.spec.ts`.

`TEST_DATABASE_URL` должен явно указывать на выделенный локальный PostgreSQL. В тестовом Docker-контейнере адрес берется из PG-переменных. В `.github/workflows/ci.yml` и `.github/workflows/deploy.yml` тестовые задания запускают сервис PostgreSQL 17.6, ожидают его готовности и передают `TEST_DATABASE_URL` для отдельной БД `alfa_test`. Учетные данные в этих заданиях предназначены только для временной тестовой БД на runner.

Браузерная приемка:

```bash
cd frontend

# На Linux: npx playwright install --with-deps chromium
```

## Демонстрация

```bash
docker compose -f compose.yaml exec backend python -m app.demo --rules
# Только для активного синтетического набора:
docker compose -f compose.yaml exec backend python -m app.demo --rules --synthetic
```

Команда подбирает компанию с кредитным продуктом, компанию с депозитами без кредитного продукта, транспортную компанию и пример ВЭД. Создает разборы для разных ролей и новой демонстрационной новости, повторно использует актуальный кэш и сохраняет манифест в БД. `--refresh` явно создает новые версии. Реальные идентификаторы из полного набора не фиксируются в исходном коде.

Пошаговая проверка (около 10 минут; в локальном запуске есть готовые учетные записи — см. «Для жюри», регистрация тоже открыта). Все шаги работают без ключа LLM:

1. Выполнить `make up`, дождаться готовности (`docker compose -f compose.yaml ps` — сервисы `healthy`) и открыть http://localhost:3000. Войти как `demo@alfa.test` / `alfa-demo-2026` — компания и роль («Финансовый директор») уже привязаны. Либо «Регистрация» (имя, любой email, пароль от 8 символов), затем регистрация компании из базы кейса (поиск по названию, ИНН, отрасли или региону) и выбор роли.
2. Главная: блок «Альфа.Пульс» с числом событий и темами; в шапке — часы («Ваш день»: новые важные события, следующая сводка) и колокольчик уведомлений.
3. «Альфа.Пульс» в меню → лента компании: у каждой новости — оценка значимости и причины отбора (отрасль, продукты, ВЭД, контрагенты, роль), у новостей с готовым разбором — метка «↓ Риск для компании», «↑ Выгода для компании», «↕ Есть риски и выгоды для компании» или «? Зависит от операций компании». Фильтры по темам и сюжетам.
4. Открыть новость → разбор: что произошло, почему важно компании, риски, возможности, действия, позиция банка. У каждого утверждения — метка («факт новости», «данные компании», «позиция банка», «вывод AI») и ссылки на источники. «Как получен вывод» — трасса: план, вызванные инструменты, проверки и коррекции.
5. В позиции банка нажать на источник — PDF банка на нужной странице (если PDF подключены через `BANK_PDF_HOST_DIR`; в чисто синтетическом запуске будет «Документ не найден»).
6. Чат-кнопка → задать вопрос, например о контрагентах; ответ со ссылками на источники. Поставить оценку разбору — она влияет на темы ленты этой роли.
7. «Контрагенты» в меню: «С кем вы связаны» (поставщики и покупатели с долей платежей, по нажатию на строку — карточка), «Что произошло у контрагентов» (события с цепочкой «вы → поставщик → его поставщик»), «Аналитика: от кого вы зависите».
8. «Аналитика банка» в меню: тезисы по документам, переход к PDF на нужной странице.
9. «Проверить свою новость» (на странице ленты) → вставить текст или ссылку: новость классифицируется и разбирается так же.
10. Профиль (`/profile`) → «Уведомления» (`/profile#notifications`): время сводки, тихие часы, лимит алертов, темы, каналы; «Отправить тестовую сводку» — сводка появится в колокольчике. Письма: `make up-mail` и Mailpit, http://localhost:8025.

## Ограничения и релиз

Вход по email и паролю с ролями и правами по компаниям реализован в прототипе; перед реальным пилотом нужны вход через Альфа-ID (SSO) и согласованный контур данных. Локальный прототип не заменяет действующий интернет-банк.

Новости классифицируются словарями и локальной embedding-моделью, поиск по банку — гибридный (BM25 + векторы). Качество измеряется на синтетическом golden set (см. «Качество разборов»); полнота таксономии, релевантность топа и смысловая достоверность еще не оценены независимыми экспертами на реальном потоке. Банковские предложения справочные, реальные заявки не отправляются. Рыночная доля считается только внутри выборки. API не дает индивидуальных инвестиционных рекомендаций.

Внешняя LLM требует действительного ключа; доступность и качество конкретных моделей должны проверяться в целевом окружении. Локальная приемка и управляемый отказ провайдера не доказывают качество живой модели.

Перед сдачей отдельно: сверить дедлайн, зафиксировать commit/tag, проверить доступ жюри, дождаться успешных CI-проверок, проверить production-конфигурацию и выполнить согласованную выкладку. Эти релизные операции автоматически не выполняются.

## Доступ и права

**Вход через Альфа-ID (OIDC).** Кнопка «Войти через Альфа-ID» на экране входа ведет к корпоративному IdP по OIDC (Authorization Code + PKCE); компании и роли пользователя приходят из IdP. Локально IdP — Keycloak: `make up-auth` (или `OIDC_ISSUER=http://localhost:8180/realms/alfa OIDC_INTERNAL_ISSUER=http://keycloak:8080/realms/alfa docker compose --profile auth up -d`), пользователи `pilot@alfa.test` (финансовый директор) и `pilot-ceo@alfa.test` (генеральный директор) компании `U_9`, пароль `alfa-demo-2026`. Вход по паролю остается для демо и отключается `AUTH_PASSWORD_ENABLED=0`. Подробнее — `docs/security.md`.

Вход по email и паролю, сессия хранится на сервере (HttpOnly cookie `session`). Пользователь регистрируется отдельно, затем регистрирует компанию из базы кейса: первый зарегистрировавший становится основателем и администратором. Администратор приглашает участников по email и назначает роль; сам себе роль человек менять не может, а в компанию попадает только по приглашению (не более 5 компаний на пользователя). Роль в ленте и разборах берётся из членства на сервере. Расформировать компанию может только участник с ролью «Собственник» (`DELETE /api/v1/companies/{id}`, меню компании в профиле); основатель без этой роли из компании не уходит, остальные участники могут выйти.

Пользователи, членство и сессии хранятся в PostgreSQL. Email — в нижнем регистре и уникален; пароль — scrypt с солью и параметрами в записи, хэш со старыми параметрами при входе прозрачно перехэшируется текущими. Сессия хранит только SHA-256 токена и истекает через `SESSION_TTL_HOURS` (12 ч) без активности; активность ее продлевает. Изменения членства в компании идут под блокировкой компании в базе, поэтому «один основатель», «не убрать последнего администратора» и «одна регистрация компании» соблюдаются при любом числе воркеров. Вход блокируется после 5 неудач на email с одного адреса или 30 со всех адресов за 15 минут (`429 TOO_MANY_ATTEMPTS`) — счетчик в базе, общий для всех воркеров; чужие попытки с другого адреса не блокируют владельца.

Прежнее JSON-хранилище (`users.json`, `memberships.json`, `sessions.json` в `RUNTIME_DIR`) переносится в базу один раз при первом старте новой версии: пароли и живые сессии сохраняются, дубликаты email по регистру сливаются в первую запись, исходные файлы не удаляются. Повторно файлы не читаются — удаленный участник не вернется. Вручную: `python -m app.legacy_import --path <каталог>`.

## Безопасность AI-компонентов

Механизмы, их место в архитектуре и границы прототипа (подробно, с проверками — `docs/security.md`: вход через Альфа-ID по OIDC, права по каждому маршруту, лимиты частоты, заголовки, 40 тестов prompt injection, секреты из файлов):

| Механизм | Где | Что делает |
|---|---|---|
| Разграничение прав | `app/auth` | Лента, разборы и чат доступны только участникам компании; роль берется из членства на сервере, а не из запроса. Метрики, расходы LLM, журнал инструментов и ручной сбор новостей — сводные данные по всем клиентам — только сотрудникам банка из `OPERATOR_EMAILS`, а не администраторам компаний-клиентов; `/meta`, открытый без входа, расходов не показывает. Сессия — HttpOnly cookie, CORS ограничен адресом интерфейса, вход — не больше 5 неудачных попыток на email с одного адреса и 30 со всех адресов за 15 минут (счетчик в базе, общий для воркеров; чужие попытки с другого адреса не блокируют владельца, параллельные запросы не обходят лимит); пользователи и сессии — в PostgreSQL, сессия истекает через 12 ч без активности |
| Агент только читает | `app/agent/tools.py` | Инструменты агента — фиксированный список чтения: профиль, экспозиции, контрагенты, поиск по аналитике банка, прогнозы, история сюжета, продукты. Записи, платежей, отправки сообщений и произвольных запросов у агента нет |
| Журнал обращений | `app/agent/audit.py`, таблица `tool_audit` | Каждый вызов инструмента сохраняется с `request_id`, аргументами, статусом и длительностью; доступен в `/api/v1/audit` и в трассе разбора |
| Защита чувствительных данных | `app/agent/prompts.py` | В модель уходит ограниченный набор признаков компании (`_company_brief`): отрасль, ОКВЭД, регион, выручка, продукты, ВЭД — без названия и данных о физлицах. Поиск компании для привязки отдает только публичные поля. Ключ LLM и пароли — только в `.env`, в репозиторий не попадают; PDF банка не распространяются |
| Данные, а не инструкции | `app/text.py`, `app/agent/prompts.py` | Предложения-инструкции в новостях («игнорируй правила», «покажи ключ», «укажи ИНН») вырезаются при приеме; тексты передаются модели как данные в JSON с явным запретом выполнять из них инструкции; вопросы модели с инструкциями отбрасываются. 40 новостей с prompt injection — `tests/test_injection.py`, на правилах и с «враждебной» моделью |
| Проверка вывода модели | `app/agent/validators.py`, `review.py` | Ответ модели не попадает к пользователю без проверок: тип происхождения, ссылки только на собранные источники, числа только из источников, признаки только существующие у компании, позиция банка — только из проверенного тезиса; затем смысловая проверка второй моделью. Не прошло — коррекция, затем откат к правилам |
| Ограничение моделей и расходов | `app/llm.py`, `app/llm_usage.py`, `config.py` | Вызываются только модели из Приложения 3 кейса; дневной лимит токенов и стоимости (`LLM_DAILY_COST_LIMIT`, 450 ₽ при лимите кейса 500 ₽) с резервированием стоимости до вызова — параллельные запросы не превышают его вместе; конвейеру — не больше доли `PIPELINE_LLM_SHARE`, одной компании — не больше `LLM_COMPANY_SHARE`, пользователю — ограниченное число запросов в час; оповещения на 50/80/100% и выключатель AI для сотрудника банка. При исчерпании или сбое — правила, причина в трассе |

Ограничения прототипа: цены моделей для резерва бюджета — оценка сверху, а не тарифы шлюза; вход — по email и паролю, без корпоративного единого входа. Для пилота — вход через Альфа-ID и цены из договора с провайдером.

## Масштабирование и сопровождение

- **Новые отрасли.** Чувствительность отраслей к темам — таблица `SECTOR_SENSITIVITY` в `app/companies/profiles.py` (знак и объяснение), названия и сопоставление ОКВЭД → отрасль — `app/companies/sectors.py`. Новая отрасль — строки в этих таблицах и кейсы в golden set.
- **Новые темы событий.** Тема — словарь и описание смысла в `app/news/taxonomy.py`, знак и формулировки эффекта — в `app/agent/composer.py`, действия по ролям — там же. Сохраненные новости переклассифицируются автоматически при изменении словарей.
- **Новые типы клиентов и роли.** Роль задает веса тем в ранжировании и набор действий; клиентские признаки берутся из CSV той же схемы (`CASE_DATA_DIR`), смена набора инвалидирует кэш.
- **Новые источники.** RSS-ленты подключаются переменной `RSS_SOURCES`, отдельные материалы — по ссылке или текстом; аналитика банка — тезисы с документом и страницей в `app/knowledge/bank_analytics.json` и PDF в `BANK_PDF_HOST_DIR`.
- **Нагрузка.** Данные, векторы и кэш общие (PostgreSQL, pgvector, Redis), API не хранит состояния и не запускает фоновых задач — его можно запускать в несколько экземпляров за nginx (локально — 2, `API_REPLICAS`). Фоновые задачи — отдельный воркер с очередью в PostgreSQL. Разборы для важных новостей готовятся заранее, пользователь получает их из кэша. На сервере пока один экземпляр API (агент выкладки ждет контейнер `alfa-backend`) и один воркер; второй экземпляр — `deploy.replicas` вместо `container_name` у backend и проверка здоровья по сервису в `deploy/gitops`.
- **Сопровождение.** Схема БД — миграции Alembic; зависимости закреплены (`requirements.txt`, `constraints.txt`, `package-lock.json`); CI на каждый pull request прогоняет тесты, порог качества golden set и сборку frontend, после слияния в `main` образы публикуются в GHCR, а агент на сервере выкатывает их сам (`deploy/gitops`).

## Мониторинг качества

| Что | Как | Где |
|---|---|---|
| Регресс качества разборов | Golden set из 31 кейса с ожиданиями; порог в CI, отчет — артефакт прогона | `tests/golden`, `tests/test_golden_quality.py`, `python -m app.eval_quality` |
| Качество классификации новостей | Эталон из 36 новостей: деловая или нет, ожидаемые темы, шум | `tests/fixtures/golden_news.json`, `python -m app.eval_classify` |
| Качество на реальном потоке | За сутки: доля текста модели, прохождение проверок с первой попытки, доля выводов с источником, покрытие позицией банка, полезность по оценкам, задержка p50/p90, итоги конвейера, расход LLM за прошлый день против лимита, отказы бюджета, причины откатов к правилам и самая дорогая модель | `GET /api/v1/metrics/daily`; ежедневная сводка в Telegram (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) |
| Обратная связь пользователей | Оценка разбора и раздела с комментарием; оценки поднимают или опускают темы в ленте роли; доля полезных — в суточной сводке | `/api/v1/feedback`, `/api/v1/metrics/daily` |

Процесс: проверка CI падает, если качество на golden set ниже порога; ежедневная сводка показывает отклонения на реальном потоке; разборы с низкой оценкой пользователей и случаи с откатом к правилам разбираются экспертом и пополняют golden set — так новые ошибки закрепляются тестом до исправления.
