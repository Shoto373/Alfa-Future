# Архитектура «Альфа.Пульс»

## Компоненты

| Модуль | Путь | Ответственность |
|---|---|---|
| ETL профилей | `backend/app/companies/etl.py` | CSV кейса → профили крупного бизнеса (stdlib, около 20 с на 85 тыс. компаний и 1,38 млн платежей) |
| Профили и экспозиции | `backend/app/companies/profiles.py`, `sectors.py` | загрузка и кэш, поиск, чувствительность компании к темам с обоснованием по признакам |
| Новости | `backend/app/news/` | таксономия, классификатор, хранилище с дедупликацией, RSS/URL-парсер |
| База знаний банка | `backend/app/knowledge/` | тезисы 9 материалов со страницами, BM25 + темы + отрасли, свежесть, противоречия прогнозов |
| Ранжирование | `backend/app/ranking.py` | скоринг «новость × компания × роль» с причинами |
| Агент | `backend/app/agent/` | оркестратор, инструменты, LLM-клиент, композитор на правилах, самопроверка, вопросы и ответы, аудит |
| API | `backend/app/api/` | REST, ошибки в едином формате, CORS, лимит тела 64 КиБ, журнал запросов |
| Хранилище | `backend/app/storage.py` | карточки, отзывы, события, метрики (JSON/JSONL в `RUNTIME_DIR`) |
| Интерфейс | `frontend/` | Next.js 16: вход, главная, лента, разбор, аналитика банка, качество |

## Данные

**Отбор крупного бизнеса.** Берутся компании с выручкой больше 15 млрд ₽ и участники надёжной группы. Надёжной считается группа, в которой не больше 50 компаний, с суммарной выручкой больше 15 млрд ₽ и собственной выручкой участника от 1 млрд ₽. На полном наборе это 380 профилей.

**Шум и неполнота.**
- Пропуск признака даёт `null`, то есть «неизвестно», а не `false`.
- Выручка, равная ровно 1000 ₽, считается заглушкой.
- «Группы» из сотен разнородных компаний помечаются как ненадёжные и не используются в выводах.
- Признак ВЭД без указанных стран отмечается отдельно.
- Собственные переводы компании самой себе исключаются из анализа контрагентов.

Все проблемы выводятся в профиле в блоке «Качество данных».

**Контрагенты.** Из платежей считаются отрасли поставщиков и покупателей с их долями, концентрация на крупнейшем контрагенте и доля внутригрупповых платежей. Если на отрасль контрагентов приходится 15% оборота или больше, её чувствительность переносится на компанию. Так событие доходит до компании через цепочку поставок.

## Агентный цикл

```
plan ──► tool × N ──► compose ──► check ──┬─► finalize
  ▲                                       │
  └──────────── adapt (≤ 2 раз) ◄─────────┘
```

1. **Планирование.** LLM (быстрая модель) выбирает инструменты из реестра. План проверяется: в нём должен быть поиск по аналитике банка. Если LLM недоступна, используется план на правилах, который зависит от тем новости: например, для ВЭД и топлива добавляется анализ контрагентов.
2. **Инструменты** (только чтение):
   - `get_company_profile`, `get_exposures`, `get_news`;
   - `search_bank_analytics`;
   - `find_related_news`;
   - `get_counterparties`;
   - `get_bank_products`;
   - `check_forecast_conflicts`.

   Аргументы проверяются по типам, лишние аргументы запрещены. На один запуск даётся не больше 16 вызовов, каждый вызов пишется в `audit.jsonl`.
3. **Контекст.** Результаты шагов складываются в общий контекст, из него строятся черновик, источники и опорный текст для проверки цифр.
4. **Черновик.** LLM (модель для рассуждений) получает контекст в JSON и обязана ссылаться только на переданные `source_id`. Если LLM недоступна, черновик строит композитор на правилах: эффект = знак чувствительности × направление события по теме.
5. **Самопроверка.** Семь проверок:
   - полнота разделов;
   - у каждого утверждения есть существующий источник;
   - позиция банка взята только из тезисов банка;
   - найдены материалы банка;
   - числа в выводах есть в источниках;
   - нет противоречий с данными клиента;
   - вывод персонализирован: опирается минимум на два признака и не повторяет новость.
6. **Коррекция.** Расширить поиск по базе знаний с учётом устаревших материалов, удалить неподтверждённые утверждения или дополнить разделы правилами. После этого проверка повторяется.
7. **Трасса.** Каждый шаг с длительностью и статусом сохраняется в карточке и показывается пользователю в блоке «Как получен вывод».

## Безопасность AI-компонента

| Риск | Мера |
|---|---|
| Недопустимые модели | Allowlist из Приложения 3, проверка имени модели перед каждым вызовом |
| Перерасход лимита | Дневной лимит токенов (`LLM_DAILY_TOKEN_LIMIT`), счётчик на странице «Качество» |
| Prompt injection из новостей | Тексты передаются как данные в JSON, системный промпт запрещает исполнять инструкции из данных, ответы проходят проверки источников |
| Опасные действия агента | Все инструменты только читают данные, реестр закрыт, аргументы проверяются, есть бюджет вызовов. Записи в данные и обращений в сеть из агента нет |
| SSRF при загрузке ссылок | Только http/https, запрет приватных, loopback и link-local адресов на каждом редиректе, лимит 2 МБ, тайм-аут |
| Утечка чувствительных данных | Профили обезличены, в журнале только метаданные запросов, аргументы аудита с маскированием текстов |
| Ответы вне назначения | Вопросы-инвестсоветы и попытки переопределить инструкции отклоняются |
| Разграничение прав (продакшен) | Пользователь привязан к компаниям через интернет-банк, роль из IAM, сервис получает только профиль своей компании. В прототипе — демо-вход |

## Масштабирование

- **Новые отрасли.** Нужен маппинг ОКВЭД → сектор и строки в таблице чувствительности `SECTOR_SENSITIVITY`.
- **Новые темы.** Добавляется запись в `TOPICS` со стемами и важностью, плюс эффекты и действия в композиторе.
- **Новые источники.** Для RSS достаточно переменной `RSS_SOURCES`. Для других форматов пишется адаптер, который вызывает `store.make_item`.
- **Новые материалы банка.** Тезисы добавляются в `bank_analytics.json`. Сканированные PDF можно распознавать моделью Qwen3-VL из списка кейса.
- **Новые типы клиентов.** Меняются правила отбора в ETL и признаки экспозиций.
- **Нагрузка.**
  - Профили строятся заранее и раздаются из памяти.
  - Ленты считаются за миллисекунды.
  - Карточки кэшируются по ключу «компания × роль × новость».
  - Для продакшена JSON-хранилище заменяется на PostgreSQL, RSS-опрос выносится в отдельный воркер, а поиск по базе знаний — в векторный индекс. Контракт API при этом не меняется.

## Мониторинг качества

| Группа | Метрики | Источник |
|---|---|---|
| Контент | доля карточек, прошедших самопроверку с первой попытки; доля выводов со ссылкой на источник; доля прохождения каждой проверки | `GET /api/v1/metrics` |
| Персонализация | открытия ленты и разборов, конверсия, доля «полезно» по разделам, комментарии | отзывы и события |
| AI | режим (LLM или правила), длительность, токены против лимита, ошибки модели | трасса, счётчик LLM |

**Процесс.**
- Каждую неделю эксперты банка размечают выборку карточек по шкале «точность / полезность / персонализация».
- Разделы с долей «полезно» ниже порога уходят на разбор. По итогам правятся тезисы базы знаний, таблица чувствительности и промпты.
- Регрессия ловится тестами `backend/tests` и сквозными проверками `tests/e2e`.
