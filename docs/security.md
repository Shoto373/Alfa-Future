# Безопасность Альфа.Пульса

Механизмы защиты, где они в коде и чем проверены. Сводка для жюри — раздел «Безопасность AI-компонентов» в README.

## Вход и сессии

| Механизм | Где | Проверка |
|---|---|---|
| Вход через корпоративный IdP по OIDC: Authorization Code + PKCE (S256). Локально — Keycloak (`make up-auth`), в пилоте — Альфа-ID теми же настройками `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | `backend/app/auth/oidc.py`, `/api/v1/auth/oidc/login`, `/callback` | `tests/test_security.py`: PKCE, одноразовый state, отказ при чужом `iss`/`aud`, просроченном токене, поддельном `nonce` |
| ID-токен получен напрямую из token endpoint по обратному каналу — по OIDC Core 3.1.3.7 проверяются `iss`, `aud`, `exp`, `nonce` без отдельной проверки подписи; состояние входа (state, verifier, nonce) — на сервере, одноразовое, 10 минут | там же | там же |
| Компании и роли — из claim `alfa_companies` («`company_id:role`»); первый пользователь свободной компании — ее администратор, следующие — участники без прав администратора; несуществующие компании и роли игнорируются | `oidc.sync_user` | `test_oidc_role_and_membership_follow_idp` |
| Вход по паролю (демо) отключается `AUTH_PASSWORD_ENABLED=0`; пароли — scrypt с параметрами в записи; блокировка подбора: 5 неудач на email с одного адреса и 30 со всех за 15 минут | `backend/app/auth/` | `tests/test_auth.py`, `test_password_login_can_be_disabled` |
| Сессия — HttpOnly cookie, `SameSite=Lax`, `Secure` на HTTPS; на сервере хранится только SHA-256 токена; истекает через 12 ч без активности | `auth/router.py`, `auth/store.py` | `test_session_cookie_is_httponly_lax_and_secure_on_https` |

## Права доступа

Роль и компания берутся из членства на сервере, а не из запроса. Каждый маршрут, где участвует компания или ее разбор, проверяет членство: чужая компания недоступна ни на чтение, ни на изменение. `tests/test_route_access.py` перечисляет такие маршруты из `contracts/openapi.json` и для каждого проверяет отказ участнику другой компании; новый маршрут без проверки роняет тест. Сводные данные по всем клиентам (метрики, расходы, аудит) — только сотрудникам банка из `OPERATOR_EMAILS`.

## Ограничение нагрузки

| Что | Лимит в минуту (пользователь / адрес) | Настройка |
|---|---|---|
| Разбор новости `POST /insights` | 30 / 120 | `RATE_LIMIT_INSIGHTS=30,120` |
| Вопрос по разбору | 20 / 60 | `RATE_LIMIT_QUESTIONS` |
| Добавление новости | 10 / 30 | `RATE_LIMIT_NEWS` |

Счетчики — в Redis, общие для всех экземпляров API (`backend/app/ratelimit.py`); превышение — `429 TOO_MANY_REQUESTS` с заголовком `Retry-After`. Отдельно: часовой лимит запросов к модели на пользователя и дневной бюджет LLM с резервированием (README, «LLM budget guards»).

## Заголовки

- Страницы (Next.js, `frontend/next.config.mjs`): `Content-Security-Policy` — скрипты, стили и запросы только со своего адреса и API, без встраивания (`frame-ancestors 'none'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`.
- API (`backend/app/api/setup.py`): те же заголовки; ответы JSON — `Content-Security-Policy: default-src 'none'`.
- nginx на сервере: `Strict-Transport-Security` (HTTPS навсегда для домена).

Проверка: `test_api_responses_carry_security_headers`; страницы — `curl -I http://localhost:3000/`.

## Устойчивость агента к инструкциям в новостях (prompt injection)

1. При приеме текст новости очищается от предложений-инструкций (`backend/app/text.py`, `INSTRUCTION`): «игнорируй правила», «системное сообщение», просьбы раскрыть ключи, пароли, данные клиентов, перевести средства.
2. Тексты новостей и материалов передаются модели как данные в JSON с явным запретом выполнять из них инструкции.
3. Ответ модели проходит детерминированные проверки: позиция банка — только из опубликованных тезисов с источником `bank:*`; числа — только из источников; признаки — только существующие у компании; вопросы модели с инструкциями отбрасываются. Не прошло — исправление, затем откат к правилам.
4. В модель уходит только разрешенный набор полей профиля (`prompts._company_brief`): без названия, ИНН и данных физлиц.

`tests/test_injection.py` — 40 новостей четырех видов (обход правил, поддельная позиция банка, запрос данных клиента, вывод служебных сведений). Каждая проходит на правилах и с «враждебной» моделью, которая выполняет инструкцию и упорствует при исправлении: в карточке нет утверждений банка без источника банка, текста инструкций, идентификаторов клиента и признаков вне профиля, а в модель не уходят поля сверх разрешенных. 40/40.

## Секреты

Ключ LLM, токен Telegram, пароль базы и секрет клиента OIDC читаются из файлов: `LLM_API_KEY_FILE=/run/secrets/llm_api_key` (Docker secrets) — значение не видно в `docker inspect` и окружении процесса. Для совместимости работает и обычная переменная (`LLM_API_KEY`), файл важнее (`config.secret`). Ключ не попадает в журналы и трассу разбора: ошибки вызова модели логируются по типу, без текста запроса и заголовков (`test_llm_key_never_reaches_logs_or_trace`). Ключи и `.env` не попадают в репозиторий: проверка в CI («Repository hygiene»).

## Ограничения прототипа

- Реальный Альфа-ID недоступен: проверен стандартный OIDC на Keycloak; подключение Альфа-ID — настройки и маппинг claim компаний.
- Подпись ID-токена отдельно не проверяется (допускается спецификацией для токена из обратного канала); в пилоте обратный канал к IdP — только HTTPS.
- Лимиты частоты без Redis считаются в каждом экземпляре API отдельно.
